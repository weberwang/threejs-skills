# three.js 技术架构

## 全局控制接入

控制面边界：可提议、可审查、可在当前用户任务的 Work Item 范围内修改，且必须回到 `$threejs-game-workflow-control` 审计和状态迁移；仅涉及外部写入、付费、真机、破坏性或外部删除、发布副作用的 A4-A6 操作请求批准。

本领域可提议、审查，并在当前用户任务、Implementation Package、A 等级和路径范围内修改；任何结果必须回到 [`threejs-game-workflow-control`](../threejs-game-workflow-control/SKILL.md) 风险门。任务内方案和路径变化同步更新计划即可继续；首次模块或边界变化先关闭事实，只有实质架构取舍才停止并 grilling。

建立可维护、可测试、可构建的 Web 3D 工程边界。浏览器是默认运行环境；只有目标渠道明确需要时，才增加小程序、桌面封装或移动原生宿主适配。

## 输入与边界

读取全局 Work Item、模块审计、依赖能力档、服务边界和项目权威工件。按 F0 范围与流程、F1 规格一致性、F2 架构质量、F3 工程验证、F4 集成/发布决策提交结果，不自行改变全局状态。

- 用 three.js、TypeScript 和项目选定的 Web 构建工具实现浏览器核心；WebGL 2 的 `WebGLRenderer` 是默认渲染器。只有项目明确选择 WebGPU 并验证目标浏览器、材质和部署要求后，才采用 `WebGPURenderer`。
- three.js `Scene` 是 `Object3D` 树，负责组织可见对象，不充当游戏状态容器。独立的场景控制器拥有玩法状态与生命周期，并提供 `enter`、`update`、`exit`、`dispose`；渲染循环按固定步长推进玩法/物理，再用渲染插值显示当前状态。
- 浏览器是默认平台。仅当目标渠道确实要求原生宿主时才采用 Capacitor 或对应宿主；平台插件按能力逐项选择并封装在适配层，不预装非必需插件。
- 小游戏必须单独验证；可选商业能力须有显式接口和已批准开关。
- 基础模块按[音频生命周期约束](../threejs-game-audio/SKILL.md#后台暂停与恢复约束)处理浏览器页面可见性和音频上下文受限；只有采用原生宿主时才添加对应平台生命周期适配。
- 基础模块按[基础显示约束](../threejs-game-orchestrator/references/game-implementation.md#基础显示约束)让 Canvas 适配实际 CSS 视口并保持 Camera、HUD 和输入坐标一致。原生窗口主题、沉浸式全屏和平台安全区只在对应宿主被选用时实现。

## 原生平台插件选型

仅在项目已选择 Android/iOS 原生宿主或明确需要原生平台能力时应用本节；浏览器项目不因此引入 Capacitor、原生工程或平台插件。

- 实现原生平台功能前先检查项目已采用的插件；满足需求时直接复用。需要新增能力时优先评估 Capacitor 官方插件或能力提供方的官方插件，再评估维护活跃、许可适用且满足需求的社区插件；领域 Skill 已指定插件时遵守该领域合同。
- 选型核实插件对项目当前宿主框架版本、目标 Android/iOS 版本、所需 API、权限和生命周期行为的支持；采用 Capacitor 时明确核对其版本。记录依赖版本、维护状态、许可、平台限制和验证方式，只安装当前需求实际使用的插件。
- 插件调用统一封装在平台适配层，通过项目公开接口向业务提供能力；业务和场景控制器不直接调用插件。Web/小游戏适配显式声明支持情况与失败语义，不以空实现伪装原生能力成功。
- 只有现有插件无法满足明确需求时才补充自建原生插件或直接原生实现；在 TDD 和实施包记录已评估插件、具体能力缺口与最小自建范围，避免重复实现插件已经提供的能力。
- 启动主题、Manifest、权限声明等必要宿主配置仍在原生工程维护。沉浸式全屏、系统栏控制和生命周期恢复等运行时能力同样优先使用插件，插件覆盖不了的部分再补最小原生代码；插件优先不降低冷启动首帧和恢复行为的验收要求。

## 执行与交接

新建游戏项目、实现基础模块或调整目录与模块边界时，先读取[游戏项目目录规范](references/project-structure.md)，按入口/基础服务分层、场景功能聚合组织代码；生成或归档产物时同时读取[产物目录与归档规范](references/artifact-storage.md)，明确临时文件、已确认成果、资源、平台、测试和工作流记录的归属，并把实际路径与所有权写入 TDD 和实施包。

1. 在实现前划分并审计模块，记录职责与非目标、公开输入/输出、状态所有权、生命周期、允许/禁止依赖、失败边界、测试和实现顺序；首次模块先完成模块门与 grilling，再按 F0-F4 写入 TDD。全局阶段、视觉硬门和场景前置以[控制模型](../threejs-game-workflow-control/references/control-model.md)、[状态、阶段与停止门](../threejs-game-workflow-control/references/state-gates.md)及对应 Schema 为准；本领域只补充模块边界。
2. 在 TDD 标注 foundation-only 的 `SHARED`/`MODULE` 范围、场景 `SCENE`/`DISPLAY_LAYER` 归属和跨场景 `INTEGRATION` 依赖。基础包只提供稳定契约，不实现具体场景玩法、HUD/布局、正式可见资产消费或 Boot→正式可见 Scene 接入；模块可按互斥所有权并行，共享契约/入口保持串行。场景控制器只通过公开服务、状态仓库或消息契约协作，不得直接访问其他控制器的内部状态。
3. 任务内新增模块、拆分职责或调整实现方案时同步更新计划与所有权，定向验证受影响部分。只有目标、对外行为或用户需要决定的实质设计取舍发生变化时才创建 Change Request 并请求决定；只有带副作用的 A4-A6 操作进入 F4 批准门。
4. 装饰性屏幕空间背景只用于非交互背景。关卡、地形、碰撞、玩法环境和相机轨迹使用独立世界数据与坐标合同，不套用 HUD 的固定设计分辨率。按[显示对象锚点与显示层分层](../threejs-game-ui-layout/references/display-object-layering.md)声明真实 `Object3D` 根、Camera、渲染顺序、深度测试、输入、生命周期和资源所有权；对象枢轴通过几何局部坐标或父级 `Group` 表达，跨层合成由 Camera/DOM/渲染通道合同明确。
5. 涉及屏幕 HUD 时使用 [`threejs-game-ui-layout`](../threejs-game-ui-layout/SKILL.md) 定义布局入口，并记录 CSS client rect、有效 DPR（最高 2）、Canvas backing、Camera、输入映射、安全区、resize、代表性视口、性能预算和证据字段。Canvas 尺寸按 CSS 宽高配置，物理像素不作为 UI 坐标；改尺寸后同步更新相机投影矩阵。传统按钮/文字优先由 DOM Overlay 布局，需在 3D Canvas 内绘制的 HUD 使用 OrthographicCamera。固定 1080×1920 设计基准只可用于 HUD；透视世界按项目单位、关卡几何、相机和视锥另立 world contract。DPR 变化时 CSS/backing 与输入映射一起更新，监听器按显示模块生命周期清理。弹窗/DISPLAY_LAYER 继承宿主 CSS 视口与输入合同；独立 Camera 或 Canvas 另行声明合成和命中映射。布局重算保持幂等；合同验证属于 F3，特殊视口与遮挡规则触发布局专项 F2。
6. 分离核心规则、表现、平台和第三方服务。公共代码和公共正式资源必须被至少两个已确认场景稳定复用，或属于运行必需；禁止无边界 `common`/`utils` 和公共素材库。foundation-only 阶段的 `SHARED` 只提供最小启动、公开契约与 Boot/Preload 生命周期，`MODULE` 只提供场景无关数据/状态/输入/资源基础设施、渲染循环和测试支撑；具体场景业务、HUD/布局和正式可见资产仍在对应场景阶段完成。每个场景在自身阶段一并完成玩法、正式视觉、全部 HUD/弹窗显示层、清理和联合证据。玩法独占规则、状态、物理语义和交互代码；美术可维护纯表现资源配置、场景数据和视觉集成调整，但不得改变玩法规则、碰撞语义或状态所有权。为浏览器输入、页面暂停/恢复、可见性、视口与目标硬件定义验证策略。
7. 对组件/资源集和场景路径，在 V1 定义每场景纹理、图集、帧数、动画采样、纹理内存、过绘、Draw Call 和最大纹理预算；在 V3 将预算写入机器清单，V4 验证正式资源与场景组合。原子资源必须引用已有适用且有效的玩法视觉契约与预算基线，否则升级路径；不得在验收时临时放宽。
8. 在 TDD 按需记录核心、移动平台、数据/API、复杂玩法、高级视觉和商业能力档；每项包含启用原因、拒绝的轻量方案、运行时性能与平台风险、验证命令和所有者。涉及服务时记录契约版本、认证授权、幂等/重试/超时、兼容、迁移/回滚、测试、监控与备份恢复；服务端不在范围时只记录外部依赖、所有者和客户端边界。
9. 在 TDD 定义本地服务身份、默认模式、主机/端口和健康检查。启动开发或预览服务前检查监听进程、命令行、项目根目录与健康状态；身份一致且健康时直接复用，不得重复启动。
10. 共享基础完成后验证代表性浏览器/Vite 启动、WebGL2 Renderer、Boot/首场景、资源和已选插件；关键玩法流完成后验证项目声明的目标浏览器/硬件；仅最终集成/G3/release 执行项目实际采用渠道的平台矩阵。不得由局部证据宣称全平台通过，不得自动发起真机验收。
11. F0 完成后提交范围与流程事实；F1 提交规格映射；F2 提交独立架构结论；F3 提交候选 SHA、实际命令证据和未覆盖项。

交给玩法开发模块入口、数据流和测试入口；交给测试提供构建命令、版本和日志定位方式。新增或修改的类、函数、实体定义均添加解释设计边界的简体中文注释。
