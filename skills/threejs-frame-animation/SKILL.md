# three.js 通用帧动画制作

使用统一生产流程，按用途选择制作、优化和人工验收规则，来源默认使用视频抽帧。视频作为动作草图；用户明确选择图片路线时，以真实生成的首尾、阶段关键帧及双图参考补帧形成序列。最终动画以游戏要求和视觉基线为准。当前 Work Item 的资源交付回到既有控制面，不另建动画状态机。

## 全局控制边界

[`threejs-game-workflow-control`](../threejs-game-workflow-control/SKILL.md) 是本技能唯一的全局状态、风险门、任务范围和证据控制面。本技能可在当前 Work Item 授权任务范围内提出动画方案、审阅现有任务工件，并仅对已分配的动画/区域和文件实施修改；真实视觉结果仍由用户人工验收，主代理负责审查方案、范围与验收证据。本技能不扩大跨 Work Item 范围，不替代控制面的批准或状态管理。所有方案、变更、人工验收结果、测试证据和阻断项都回到唯一控制面登记与复核，再按控制面安排完成 ThreeJS 接入、运行验证和状态迁移。

在当前 Work Item 范围内先内部推导并维护动作时间轴设计记录。方案完成后，按[设计理念说明](references/intent-driven-design.md#方案完成后阐述设计理念)向用户说明目标感受、关键动作依据、节奏和资源取舍，并等待用户明确确认当前方案；确认后才编写正式提示词和制作真实素材。方案确认与视频、图片关键帧及完整序列的真实素材验收分别进行。只有玩法事件、时长或行为权限确实缺失且无法推导时，才询问受影响动作。

## 适用范围与运行时

此技能生产二维逐帧位图动画，运行时以 `THREE.Sprite` 和 `THREE.SpriteMaterial` 显示为朝向相机的 billboard；可用于世界空间角色/特效，也可接入现有正交相机或 HUD 图层。HUD 的布局、缩放和输入仍沿用项目现有 UI 系统。本技能不制作三维骨骼模型动画；带骨骼、蒙皮或模型动作片段的资源使用 three.js `AnimationMixer`。角色若有意采用二维精灵表现，仍走本技能的图集路线。

## 分类入口

每个动画先确定用途类型，只读取对应分类参考；多类型批次逐区域选择规则，不默认加载四份文档。

| 用途类型 | 选择依据 | 读取参考 |
| --- | --- | --- |
| 普通动画 | 物件、环境、装饰、机械运动与状态变化 | [普通动画](references/object-animation.md) |
| 角色动作动画 | 待机、移动、攻击、受击、跳跃等身体行为 | [角色动作动画](references/character-animation.md) |
| 特效动画 | 命中、爆炸、烟尘、光效、状态效果等视觉反馈 | [特效动画](references/effect-animation.md) |
| UI 帧动画 | 按钮反馈、提示、图标等需要逐帧位图资源的界面动效 | [UI 帧动画](references/ui-frame-animation.md) |

用途类型不决定来源路线、行为单元、生成批次数量或运行时动画 key 数量。循环、单次、组合、终态保持是各类型共用的播放参数，可按任务组合使用。角色动作可进一步按循环运动、主动行为、被动反应和连续组合选择规则，不为每个动作新增技能。简单程序 UI 动效按既有 UI/程序路线处理。

## 来源路线

用户未指定来源时默认使用视频抽帧，并在内部动作时间轴记录中注明；图片递归补帧仅在用户明确选择或确认切换时启用。沿用当前任务明确选择的来源；来源切换按既有变更边界处理并更新内部记录，不因默认值变化丢弃已确认成果。视频来源或生成能力暂缺时报告缺口，不能自动改用图片路线。两条路线共用分类、游戏时间轴和人工验收，只读取当前来源细节。

| 来源 | 适用依据 | 按需读取 |
| --- | --- | --- |
| 视频抽帧（默认） | 使用真实视频作为连续运动草图；选择有效区间并按阶段重定时后抽帧 | [视频节奏整理](references/action-timing.md#视频节奏整理)、[按区域抽帧](references/region-planning.md#按区域抽帧) |
| 图片递归补帧（明确选用） | 用户选择逐个控制关键姿态、造型或透明边缘；固定画布依次制作首尾、必要关键帧，再用相邻两图生成指定帧位 | [图片递归补帧](references/image-inbetween.md) |

图片路线的“插帧”是带双图参考和指定动作时点的图片生成，不是保证几何正确的光流插值。跨视角、接触、遮挡或相同首尾的循环先补必要关键姿态，再递归；不只凭首尾推断完整复杂运动。

## 共用流程

1. 读取视觉基线、用途类型参考、[完整动作与时间轴](references/action-timing.md)，建立当前动画的内部设计工件。明确来源路线、行为边界、初态/终态、游戏时长、阶段区间、关键姿态、事件、播放方式、锚点/允许位移、完整运动范围、目标显示尺寸、FPS、资源预算和背景处理。角色动作还须明确前后动作衔接、是否循环及进入/退出条件，见[衔接与循环设计](references/character-animation.md#衔接与循环设计)。按需要读取[区域规划](references/region-planning.md)，合批时各区域仍有独立类型、有效时长和时间映射。
2. 按[动作分析规则](references/action-timing.md#动作分析与时间轴)和[玩法与意图设计方法](references/intent-driven-design.md)，从玩法目的、观看体验与已有时间约束内部推导行为边界、阶段、运动依据、衔接/循环、节奏和性能取舍，并记录具体时间轴、事件时点、关键姿态意图、尺寸推理和逐阶段检查点。视频同时推导 768p/2K 区域排布、条数、整组消耗与推荐方案。方案完成后先向用户阐述设计理念并等待当前方案明确确认；只对确实缺失且无法推导的玩法事件、时长或行为权限提问，并只暂停受影响动作。不制作灰盒或可播放几何示意。
3. 确认当前方案后，按“共用视觉与资源约束＋类型规则＋当前动画参数”编写正式提示词，并在已有操作授权范围内制作真实候选或预览。视频按[分辨率与合批比较](references/region-planning.md#视频条数与消耗比较)选择 768p 或 2K：先最少条数覆盖全部动作，再在该条数下选整组消耗最少者，同等条件优先 768p；图片按[图片分辨率约定](references/region-planning.md#图片分辨率约定)处理。确认前不生成真实候选或调用图片生成；真实素材交付时附简短检查点。用户确认实际素材时可同时接受该素材所表达的时序，不另行确认文字复述。已有生成授权不能替代当前方案确认，方案确认也不扩大外部操作授权。
4. 视频路线接收真实视频并核对画布、区域和音轨，按需要选择有效区间、阶段重定时并保存派生来源，交付用户人工验收实际最终抽帧输入。原视频已适配时直接验收原视频；只有实际视频内容、区域和时间映射已经人工验收才抽帧。SHA 可作为追踪记录，不参与文件验收或替代用户对实际视频的确认。未通过先修正并重提；修正说明或文字方案不代替新视频验收。图片路线核实实际输出尺寸，固定统一画布并确认首尾；同一连续行为的必要关键帧按时间顺序逐张制作，与真实基线及相邻已确认帧比较，人工确认当前帧后才推进下一关键帧。关键帧齐备并确认后，再按内部推导的时点递归补齐目标帧位。实际依赖与[一致性及衔接门](references/image-inbetween.md#关键帧的一致性与衔接门)集中维护；父图有缺陷先修正，不继续传播。
5. 视频按固定区域抽帧，图片按真实来源清单打包；两者共用背景处理、等比缩放、固定 cell/锚点、独立图集、报告和 HTML 预览。依据当前类型反馈局部修帧，保留已有修图成果及来源身份，更新图集、报告、预览及可选 SHA 追踪值。缺陷修复不默认替换整组来源。
6. 用真实完整帧序列按内部设计工件中的逐阶段检查点人工检查表现意图、节奏、连续性、事件及单次/循环/终态和外部动作衔接，记录具体偏差与用户结论。同一已确认目标下的局部纠错直接返修并展示前后对照；目标感受、核心动作方案、玩法语义或来源路线实质改变时，先重新说明并确认。已有方案范围内不重新索取生成授权。保存分类规则、玩法与意图推导、方案确认版本、真实候选审阅、时间映射与最终人工验收证据，按[工作流接入合同](references/workflow-integration.md)提交资源，再回到控制面完成 ThreeJS 接入和运行验证。

## 动作设计与真实素材确认

动作分析与时间轴写入内部设计工件；方案完成后先说明设计理念并等待用户明确确认，确认后才进入正式提示词与素材制作。方案确认之后，视频路线由用户审阅真实视频候选及完整序列；用户对实际视频的确认可同时接受其中表现的时序。图片路线以真实首尾、关键帧和递归父图逐张确认，再验收完整真实序列。真实序列预览提供播放/暂停、重播和逐帧查看，检查标记只放预览界面。正式美术使用真实基线及已确认素材，设计图表和历史占位示意不得作为生图视觉参考。同一已确认目标下的局部修正直接返修并展示前后对照；目标感受、核心动作方案、玩法语义或来源路线实质变化时，先重新说明并确认。详细要求见[动作设计与素材确认](references/workflow-integration.md#动作设计与素材确认)、[真实素材审阅与验收](references/workflow-integration.md#真实素材审阅与验收)及[设计与美术的边界](references/workflow-integration.md#设计与美术的边界)。

## 共用质量与关键约束

- 以可读性、节奏、主次关系、连续性和事件同步验收；具体判断及优化方法见[共用质量与优化](references/action-timing.md#共用质量与优化)。重量感、夸张程度、停顿和跟随运动按类型、对象性质与视觉基线配置，不统一套用战斗节奏。
- 每个动画的时长与节奏先依据游戏特点、玩法响应、对象性质和表现目的独立确定。同一视频中的多组动画可以有不同总时长、阶段比例、停顿、循环周期和 FPS，不为合批强行统一；具体规划见[游戏时间先于来源](references/action-timing.md#游戏时间先于来源)。游戏时间独立于源视频时长，同一完整行为共享自己的时间轴，内部可标事件和输入衔接；制作分组不增加攻击次数、自动连击或伤害，也不改变现有输入机制。
- 时长、阶段比例、命中停顿、连击次数与音频均由当前任务确定；具体动作和参数案例不能成为全局默认要求。视频在 768p/2K 中按实际区域排布、条数与整组消耗选择，不以固定档位、压缩运动范围或丢失必要细节凑批次。图片分辨率约定保持独立。图片序列没有视频音轨，声音独立绑定事件。
- 默认保持要求呈现的内容及完整运动范围入框，保留安全边距。裁剪例外须有当前任务的明确授权，逐项记录对象、范围与理由；不能为合批或强调力度自行裁边。
- 稳定锚点不等于禁止运动。允许位移、姿态夸张或形变须在设计工件中说明范围和意图，按计划验收；禁止未计划的漂移、闪烁、比例变化与跨区串入。
- 固定画布、相同锚点记录和来源校验通过，不证明实际对象尺度、支撑位置或动作连续。图片路线先确认当前帧的类型相关状态与相邻衔接，再放行依赖它的制作；不能以增加补帧、逐帧缩放居中或静止复制替代纠错。
- 背景处理按素材边缘与类型选择。颜色去背景只用于已确认的纯色硬边；半透明、发光或未知边缘使用真实 Alpha、遮罩或帧图片修正，不冒充硬边确认。特效、声音和镜头反馈是否烘入按任务合同决定。
- 分类与优化参数保存在设计工件，不因分类添加合同字段，不虚构脚本或生成 API 参数。视频沿用原合同；图片使用独立来源清单、报告和 accepted 合同，记录真实生成图、父图、时间槽位、生成/修图记录及可选 SHA 追踪值，不能伪造视频路径或来源时间戳。
- 时间轴推导记录在内部工件；人工确认聚焦真实视频、图片关键帧和完整序列，文件门只验证结构与身份。不得自动截图或启动真机验收，外部写入、付费、发布沿用独立授权边界。

## 执行代理

帧动画按用途分配专业设计职责，并由对应设计师完成时间轴细化、提示词、时间整理、抽帧/图片序列集成和修正：

| 用途类型 | 负责设计的职业 | 设计重点与交付依据 |
| --- | --- | --- |
| 普通动画 | 道具与环境动画设计师 | 物件材质、结构与运动机制、机械约束、环境节奏、状态转换和循环接缝；交付关键状态、运动轨迹与锚点范围。 |
| 角色动作动画 | 角色动画设计师 | 身体力学、重心与支撑、动作剪影、预备与跟随运动、角色性格及前后动作衔接；交付关键姿态、接触关系与玩法事件时间轴。 |
| 特效动画 | 游戏特效设计师 | 视觉层级、能量演变、形状与色彩节奏、透明边缘、命中同步和消散；交付效果阶段、峰值时点与角色/场景遮挡约束。 |
| UI 帧动画 | UI 动效设计师 | 交互状态、反馈时机、注意力引导、文字与图标可读性、打断及重复触发；交付状态转换、反馈时间轴与界面显示边界。 |

职业身份写入委派任务包和设计工件；按动画用途分配，不按来源路线、文件格式或播放方式分配。混合任务按可独立设计的动画或区域明确职业、文件所有权和负责范围，交接跨类型事件时点、坐标/锚点、遮挡关系与上下游依赖；依赖尚未交接时不并行，仅在文件所有权不重叠且依赖已交接的工作间并行委派。共享视频合批不合并职业职责，也不改变各动画独立时长。

主代理负责需求、任务包、人工反馈、接入范围、审查与最终验证，不接管动画制作。

使用 `collaboration.spawn_agent`，设置 `agent_type="default"`、`model="gpt-6.1-sol"`、`reasoning_effort="max"`、`fork_turns="none"`。完整任务包包含 Work Item、用途类型与来源路线、负责职业及动画/区域所有权、跨类型事件/锚点/依赖交接、对应参考、玩法目的与表现意图、既有玩法时间约束、行为/输入边界、独立区域时间轴、性能预算与检查点、素材与基线路径、允许修改范围、当前候选版本/内部时间轴、允许推进步骤、验收标准、测试等级与命令、禁止操作及并行提醒。先交付简短中文设计理念说明并等待用户确认当前方案；确认后才推进正式提示词和真实素材。视频路线还须交接当前真实输入视频及人工审阅结果，图片路线交接当前已确认帧和已有生成授权。图片生成/编辑另交 `image_generator` 子代理，动画执行代理负责约束与集成。

同一工作项的连续修正优先复用代理；范围实质变化或工作项完成后结束该生命周期。位图生成/编辑仍交给图片生成代理，动画执行代理提供时间轴、帧槽位和素材约束并集成结果。指定工具或模型不可用时报告限制，不静默换模型。委派不扩大文件、视觉自动验证或外部操作授权。

## 本地工具与参考路由

视频抽帧需要 `ffmpeg`、`ffprobe` 与项目 `sharp`；图片规划只使用 Node.js，图片打包使用 `sharp`。先查看当前路线的实际工具帮助：

```powershell
node <skill-dir>/scripts/video-to-atlas.mjs --help
node <skill-dir>/scripts/image-inbetween-plan.mjs --help
node <skill-dir>/scripts/images-to-atlas.mjs --help
```

视频工具每次处理一个区域（省略则为整画布），覆盖完整输入时间段；`--fps` 同时控制抽样与播放，没有时间剪辑或独立逐帧时长参数。图片规划先确定游戏时长、FPS、关键帧位和递归依赖；图片打包从来源清单取 FPS/loop，只处理实际图片，不生成素材。时间问题先按共用时间轴修正设计与来源，不只改报告。

| --- | --- |
